# Redstart — Changelog

Rolling, human-readable log of changes to the Redstart Nest / Redstart Twig codebase (formerly Beaver Dam / Beaver Log — see the 2026-07-13 rebrand entry). Not a replacement for `git log` — this is for context that helps troubleshooting later: *why* something changed, not just *what* diffed. Newest entries at the top.

---

## 2026-09-03

- **The headless admin plane.** Redstart Nest stopped being a desktop app that happens to run a server and became a **daemon that happens to have a window**. Eight phases on `feat/headless-admin-plane`; the design record and the phase-by-phase implementation notes are working notes, so the reasoning worth keeping is summarised here and in [Architecture → The daemon and the control plane](docs/architecture.md#the-daemon-and-the-control-plane).
  - **A control plane on its own port (`:19083`), with its own lifetime.** Modelled on the beacon, not on the gateway: it binds when the daemon starts and stays up whether or not a model is running. That single test is what decided it should be a separate listener rather than an `/admin` prefix — *a plane whose lifetime is tied to the thing it controls cannot be used to start that thing.*
  - **Authentication is mandatory there, and separate.** The listener never reads `authRequired`, so turning login off for the chat UI does not open process control. It accepts only sessions its own login route minted — never an API key (those live in tool-client config files) and never a gateway session, so an owner signed in to the chat UI does not thereby hold the power to spawn processes. Control-plane sessions carry 12 sliding hours against the data plane's 30 days: thirty days of standing access to something that starts and stops processes is exactly the number nobody revisits once shipped.
  - **The preload bridge is gone.** A launcher that has to be servable to a browser cannot reach the main process through Electron-only plumbing, so `contextBridge`/`ipcRenderer` were replaced by an HTTP client against `POST /admin/api/<namespace>/<method>`. One route per method rather than a single `/rpc`, because distinct paths make the surface enumerable from the outside — a reviewer, a proxy log and a firewall rule can each name what they are looking at. The gate sits in front of dispatch, so a route added later is gated by default rather than by whoever remembers.
  - **No CSRF token, as a conclusion rather than an omission.** The credential is a bearer token the page attaches itself, never a cookie, so a cross-site request carries no authority; and the listener sends no CORS headers, so a foreign page could not read the response even if it could send the request.
  - **The static layer is an enumerated allowlist**, built off disk at startup and looked up by exact match — `..` traversal is structurally impossible rather than filtered. Symlinks inside the bundle are never followed. Deliberately *not* reusing `isPublicAsset()`, which is a proxy rule for llama-server's route table and must never learn about admin paths.
  - **A per-box setup code replaces the anonymous first-admin path.** The old IPC-only handler granted ownership to any caller when no owner existed, which was safe only while IPC was its sole door — on a LAN-reachable route, "no owner exists" is reachable by *corruption* as well as by newness, and first-to-arrive would own the box. One CSPRNG token per unit, generated on that unit, opening one route that both creates and resets the Owner. Stored in plaintext **on purpose**: it is a physical recovery credential, like the label under a router, and anyone who can read that file could rewrite `accounts.json` by a shorter route anyway. Do not "fix" it by hashing it.
  - **The daemon runs without Electron.** `bin/nestd.mjs` boots the same server under plain Node. Two fail-closed seams made it possible — `platform-paths.mjs` (where state lives) and `secrets.mjs` (what encrypts a credential) — with the desktop injecting `app.getPath` and `safeStorage`, and the daemon injecting a directory and an AES-256-GCM key file. `secrets.mjs` was the single hardest blocker: it sits on the daemon's critical path, so nothing booted without it.
  - **Config and user content are two subtrees, enforced at startup.** A config reset must never be able to wander into someone's documents, and a backup has to be able to treat "my settings" and "my files" as different questions. Overlapping directories are refused at `initPaths()` rather than collapsing quietly.
  - **Closing the window stops nothing.** The model stays available to everyone else on the network and reopening reconnects to the running daemon. Stopping is deliberate — **Shut down**, the tray's **Quit**, a signal, or `npm run daemon:stop`, which finds the daemon through a pid file written *after* the control plane binds (so a second daemon that loses the port race cannot overwrite a live entry) and refuses to signal a pid whose identity it cannot confirm.
  - **Lifecycle calls are serialised.** A daemon reachable from the tray, a browser and the Electron window at once makes concurrent `launch`/`stop` routine rather than contrived. Same-kind callers share one in-flight promise; launch and stop are also ordered against each other, after a race was found where a stop landing between `spawn()` and `startGateway()` left the public port listening in front of a dead server while the UI reported stopped.
  - **Exposure is an address, not a boolean.** `adminBindHost` defaults to loopback; one setting covers a LAN address, a VPN interface, a management VLAN or the wildcard. Hostnames are refused rather than resolved — "bind to whatever this name resolves to right now" is not a stable exposure decision.
  - **mDNS was retired.** Android's resolver never answered `.local` lookups for browser navigation, so the name failed on the platform most clients are, and Twig's beacon scan never depended on it. The port-80 clean-URL proxy survives and is Windows-only.
  - **Deployment artifacts for a box nobody logs into** — a systemd unit, the Windows SCM procedure, and a Caddyfile that terminates TLS in front. **None has been run on real hardware**, and `deploy/README.md` says so at the top.
  - **Documentation swept for accuracy** against the shipped code rather than the plans. Corrected: sessions described as in-memory in three places (they persist, hashed, with per-plane TTLs), the retired mDNS advertiser still in the README topology, the Owner-creation walkthrough pointing at a sidebar panel that no longer exists, "Windows only for the server" without the daemon qualifier, the state-file list predating the config/data split, and `development.md` describing the launcher as talking IPC. Several roadmap items — headless mode, a web admin UI, admin access from another device, auto-start on boot — moved from planned to shipped.

## 2026-08-18

- **MCP plugin system.** Redstart Nest can now install a third-party stdio MCP server — an admin browses the [official MCP registry](https://registry.modelcontextprotocol.io) or names a package directly, and its tools appear namespaced (`<plugin-id>__<tool-name>`) alongside the built-in capabilities, under the same classification and policy machinery every one of those already uses. PR [#26](https://github.com/ImDeadWeight/redstart-project/pull/26). Full docs: [Capabilities → Plugins](docs/capabilities.md#plugins), [Security → Plugins](docs/security.md#plugins).
  - **Four sources.** A pinned npm package, a pinned pypi package (installed via [`uv`](https://docs.astral.sh/uv/)), a local folder already on the machine, or a raw command for anything else. Registry metadata pre-fills which environment variables a server needs, when available.
  - **Two switches, both required (D-a).** The Plugins tab's `enabled` is the install-level master switch; the Tools tab's card is per-profile activation — exactly the two-key model every built-in capability already uses. A plugin can be installed and "healthy" while contributing zero tools to any profile, and that is by design, not a bug.
  - **Fail-closed classification (D3/D-b).** A plugin's tools are third-party code nobody here wrote or reviewed, so every tool a fresh install discovers starts `destructive` — refused everywhere — until an admin reads its actual description and promotes it. The child's own self-reported `readOnlyHint` is never trusted for this; only an admin's explicit action moves a tool out of the fail-closed default. A new **bulk-classify** action ("Set all N to: read, Apply to all") makes this practical on a plugin with dozens of tools, with per-tool overrides staying available for the exceptions.
  - **Credentials are disclosed, not just encrypted.** A plugin may hold an API key for a third-party service (a stdio server is just a local process — nothing stops it opening outbound HTTPS). The key is encrypted at rest the same way as the Postgres connection string, but the encryption shipped together with a `deriveEgressFacts` change in the same commit, specifically so the two could not ship separately: a plugin holding a key is now reported as network egress at `GET /egress` and in the system prompt, exactly like an external MCP server. Landing credential support ahead of that disclosure was treated as not shippable.
  - **A real production bug this surfaced, found by installing real third-party plugins (comfyui-mcp, calculator-mcp-server, `@modelcontextprotocol/server-memory`) rather than trusting fixtures:** a plugin could be correctly enabled on both switches and still advertise zero tools to the model, with nothing anywhere saying why — every tool was still sitting at the fail-closed `destructive` default, silently filtered by the policy gate. Fixed by having the Plugins tab compute and show an advertised-vs-discovered count ("0 of 40 tools currently reach the model") whenever the two differ.
  - **Three more bugs found the same way.** The install wizard's registry-pick path could silently overwrite a plugin's derived id with the literal string `"plugin"` (a seed-fallback ternary had no case for a registry-sourced install). An install failure could render in the dialog as the literal text `"undefined"` (two different failure shapes from the IPC layer, only one of them handled). And a profile's `activeToolIds`/`disabledToolIds` never took effect on an already-running server without a full restart — unlike capability and plugin-registry toggles, which do — because `buildGatewayConfig()` read those settings from a snapshot frozen at launch rather than a live source; a new `server:sync-tools` channel closes that gap, gated on the profile being edited actually being the one that's running.
  - **Python/pypi plugins, via `uv`.** A second install resolver alongside npm's — `uv tool install` into an isolated per-plugin directory (`UV_TOOL_DIR`/`UV_TOOL_BIN_DIR`), spawning the resulting console-script shim directly. Verified against a real `uv` install and real pypi packages throughout. Caught the same day: uv writes its entire progress and summary output to **stderr**, the opposite of npm's split — the first implementation parsed stdout (always empty for uv) and every real install silently failed despite uv itself succeeding, caught by a test that installs a real package rather than mocking uv's output.
  - **A second real bug, found by this branch's first-ever CI run:** `detectNpm()` only worked on Windows. It derived npm's location as `<node-dir>/node_modules/npm/...` — correct for Windows' ZIP distribution, where npm sits beside `node.exe`, but wrong for the POSIX layout every other install method uses (`<prefix>/bin/node` + sibling `<prefix>/lib/node_modules/npm/...`). This had apparently been broken since the feature's npm installer first landed; it simply never ran anywhere but local Windows dev until the branch was pushed and CI ran against it for the first time.
  - Every discovered tool's own description is now shown in full (not truncated) in both the install wizard's classify step and the Plugins tab's per-plugin editor, alongside a class-count summary and a color-coded border per class — a 40-tool plugin previously read as an undifferentiated wall of "destructive" with no way to judge what to promote.
  - The Plugins tab sits before the Tools tab in the launcher's tab order (moved after initial shipping, on request) — installing and governing a plugin happen in one place, activating it for a profile happens in the other, and the split is meant to read as that division rather than as redundant controls.
  - `npm run test:security`: 695 checks, up from the pre-feature baseline of 644 — all fixture-driven where the plan called for it (a controllable stdio MCP fixture with normal/silent/exit-on-call/no-tools/auth-fail/env-echo modes) and network-dependent-but-skip-clean where a real install genuinely needed one (real npm/pypi packages, both skip cleanly rather than failing the build when the registry or the runtime isn't reachable).

## 2026-08-14

- **Per-account roles.** Every authenticated account previously got the identical tool set — whatever the running profile enabled — and the `role` field granted no capability at all. An admin can now create named roles under **Settings → Roles**, set what each may reach, and assign one per account. Plan and reasoning in `docs/notes/roles-and-permissions-plan.md`.
  - **Two axes, not one.** `role` was doing double duty as management authority and identity, so it is now `tier` (`owner`/`admin`/`user`, still what `canManage()` reads) plus a separate `roleId`. Collapsing them would mean every management check needs an opinion about where an admin-invented "Legal Team" sits in a hierarchy. `toPublicAccount` emits **both** `tier` and a mirrored `role` for one release: Twig/Blueprints/Yellowscript each hold their own copy of the login response shape, and an undefined `role` there reads as "not an admin" — a failure in the confusing direction.
  - **Roles restrict, never grant.** Effective access is `(configured globally AND activated by the profile) ∩ role`. Enforced as a property rather than a convention: every rule in the new `permissions.mjs` narrows, and `scripts/test-roles.mjs` runs 2000 randomised config × role pairs through a field-by-field comparison that fails on any widening. Several of the rules look equally plausible written backwards (`whitelistEnabled: global || role forbids bypass`; `allowWrite: global && role`; `maxFetchTokens: min()`), and every inverted version widens access silently — **verified non-vacuous by mutation**: flipping `allowWrite` to `||` fails on case 0 with a reproducible counterexample.
  - **The feature is inert on upgrade, and that is the acceptance test.** Full Access has permission set `{}`, `roleId: null` resolves to it, and an empty permission set is asserted to be an exact identity over the config. Existing installs behave byte-identically until someone assigns a role.
  - **One narrowed config, threaded where the global was.** `activeToolsConfig` is a single module global every connected client is served from, so the whole change is deriving a per-account copy and passing it through. `evaluateToolPolicy` needed no new parameter — it already took a config. In the gateway, one `effectiveConfig` covers the completions proxy, the injected system prompt, `/redstart/mcp-servers`, the file explorer and the download route, so a restricted account gets a consistent answer wherever it asks.
  - **Roles deliberately do not reach client-app tools.** Twig's `fs_*` names are unknown to `CAPABILITY_TOOL_NAMES` and fall through the strip by construction. Writing files on the user's own PC is the entire point of Twig; an admin restricting what an account may do to the *server* must not disable the user's local editor. Banning a client app stays an org-wide decision. There is a test asserting role narrowing never touches those names.
  - **Fail posture is explicit in three directions.** Auth off → unnarrowed (the toggle keeps meaning what it says). Owner → unnarrowed and unassignable (anti-lockout). But login on *and* no identity at the dispatcher → narrowed to nothing, because that is a plumbing bug rather than a posture, and the auth-off branch would hand a broken code path the full tool set.
  - **That third case was live, from the in-flight Streamable HTTP migration.** `transport.handleRequest(req, res, parsed)` was called without ever setting `req.auth`, which the SDK reads to populate `extra.authInfo` — so `ctx.account` was always `null`. Beyond roles, that also collapsed per-account file storage to the anonymous scope for every MCP tool call. Fixed by assigning `req.auth` before the handoff; the `DENY_ALL` fallback above is the belt to that braces.
  - **Surfaces are honest about their limits.** A per-connector key binds its surface at issue time. A password session is tagged `nest-chat` (the chat UI is what logs in that way, but any client posting credentials gets one). An account-wide API key names no app — so an account whose role restricts surfaces cannot hold one, refused in both the admin and self-service paths rather than left as a caveat in the docs.
  - **Admin tier splits into `manageAccounts` / `manageRoles` / `managePromptBlocks`** — exactly the three that exist as HTTP surfaces, not an invented taxonomy. Server/model/capability config stays IPC-only at the host machine, which is also the permanent escape hatch if a role edit goes wrong. Tier stays the ceiling: no role can make a User an admin, and an admin cannot assign authority they do not hold themselves.
  - Deleting a role reassigns its members to Full Access in the same operation, and role writes drop live MCP sessions so a connected client re-lists rather than offering tools that now get refused.
  - `test-contracts.mjs` caught the public-account shape change, and `test-ci-parity.mjs` caught the new suite being unwired from `ci.yml` — both did exactly their job. 27 checks in `test-roles.mjs`.
- **Tools tab unified into one card per tool, each with a single Enable/Disable.** Two overlapping controls existed for every capability — a per-profile checkbox list under "Local Capabilities" plus a separate global Enable/Disable on each capability's own card — and Web Access had no card at all, just a special-cased section at the top of the tab. Now there are eight uniform cards: Web Access, Postgres, Documents, SQLite, Vault, Git, File System, Scholar. Spec in `docs/notes/tools-tab-unification.md`.
  - **Web Access needed its own flag, not `activeToolIds` membership.** Every capability defaults OFF by absence from `activeToolIds`; web access was the opposite — hardcoded on for every profile, with no flag anywhere. Expressing "enabled" as `activeToolIds.includes('web_access')` would have silently turned web access off for every profile saved before this change, since none of them carry that entry. New `ProfileTools.webAccessEnabled` is read `!== false`, so an absent key still reads as on.
  - **Disabling the new Web Access card would have silently done nothing, and the bug was already latent in the whitelist-on path.** `web-fetch-tool.mjs`'s `fetchEnabled` only consulted the `enabled` flag when the whitelist was OFF; with the whitelist ON — the default — the only gate was whether any source was selected. Harmless while `enabled` was hardcoded `true` in `buildGatewayConfig`, but exposed the moment it became a real per-profile switch: a user on default settings who had sources selected and then pressed Disable still got both web tools served. `enabled` is now a precondition in both branches.
  - The seven capabilities' global `enabled` flag is now vestigial — `buildGatewayConfig`'s `*Wanted` checks dropped it, kept only in storage/IPC shapes for back-compat (`tools.json`, `capabilities:get`). A capability produces tools once it is configured (a folder or connection string) **and** its card is enabled for the profile — one gate, not two.
  - Two new `buildGatewayConfig` tests (a legacy profile with no `webAccessEnabled` key keeps web access; `webAccessEnabled: false` is honoured) plus one proving the whitelist-on Disable bug above is actually closed, not just moved.
- **Custom web sources and external MCP servers could be added but never edited — delete-and-recreate was the only path.** Found on hands-on testing of the new Tools tab. Both now have an Edit button that reopens the same add form pre-filled. Editing keeps the entry's original id rather than re-deriving one from a possibly-changed name — a rename that got a fresh id would fork into a duplicate and silently orphan every `activeToolIds`/group/role reference still pointing at the old one.
- **External MCP servers gained API-key auth, which surfaced a real bug in the connection test.** Tried against DeepWiki's public no-auth endpoint and Context7's API-key endpoint as acceptance targets, per the project's own "OAuth is the big open question" framing.
  - DeepWiki connected fine over the wire but `mcp:test-external` reported it as broken — `Unexpected response: 200 (text/event-stream, not JSON)`. It only ever tried `res.json()` on the body; DeepWiki's server, correctly per the streamable-HTTP transport spec, is allowed to answer a JSON-RPC POST with an SSE-framed body instead of plain JSON, and several real servers do. New `parseMcpResponseBody()` in `external-mcp-url.mjs` handles both framings, including SSE's multi-line `data:` join. Five new unit tests, one reproducing the exact DeepWiki shape.
  - **Caught before it shipped: the first working version of this stored the key in `tools.json` as plaintext.** It passed the full suite, because nothing was asserting otherwise — the gap surfaced on a pre-commit review of the diff, not a test failure. Fixed the same way the Postgres connection string already is: encrypted at rest via `secrets.mjs`, never sent back to the renderer once saved (`mcp:list-external`/`mcp:add-external` report `hasApiKey`, never the key), decrypted server-side by id when the connection test needs it. New bridge-projection test mirrors the existing Postgres one, so a regression here fails loudly next time.
  - **OAuth-protected servers (GitHub's official remote MCP server, for one) are still not supported** — there is no authorization-code flow. Documented as an open gap in `docs/capabilities.md` rather than left silently absent; `docs/notes/mcp-streamable-http-migration.md` already sketches the shape a fix would take (the official MCP SDK's `OAuthClientProvider`, not a hand-rolled implementation).
  - `mcp:test-external` no longer throws on a `null` argument — destructuring `null` throws where a default-parameter form only catches `undefined`. Caught by the IPC guard suite's existing fuzz test, which sends exactly that.
- Installed `electron-devtools-installer` for the dev launcher (React DevTools' Components/Profiler panels), gated behind `!app.isPackaged` so it neither runs nor ships in a packaged build.

## 2026-08-10

- **The renderer → main IPC boundary had no sender validation, and two calls from a compromised renderer reached `spawn()`.** Raised as the single P0 of an external risk assessment; verified against the tree and found real but under-specified — the review named the missing control without naming either the escalation path that makes it exploitable or the navigation gap that would deliver an attacker into the renderer to begin with. Both are now closed; the reasoning is in the sub-points below.
  - **The chain was `settings:set-binary-path` → `llama:launch`.** The first wrote any renderer-supplied string to `settings.json` with no validation of any kind; `resolveBinary()` checked `fs.existsSync()` and nothing else; `ipc/server.mjs` spawned it with `cwd` set to its own directory. No dialog, no consent, no user interaction. `models:download` + `settings:set-models-dir` extend it to *fetch* the payload first. That is the blast radius the whole change is sized against: RCE, not config tampering.
  - **Severity stated honestly: there is no XSS in the launcher today.** Zero `dangerouslySetInnerHTML` in `src/`, React escapes by default, so the network-sourced content that does reach the renderer — Hugging Face search results, GitHub release notes, streamed llama-server log lines — is inert. This is defense-in-depth against a future renderer bug plus one live SSRF (below), and it should not be described as an incident. It was worth doing before the alpha ships because the cost of being wrong is arbitrary code execution and the fix is small.
  - **Navigation containment was missing entirely and is the cheaper half.** A grep for `setWindowOpenHandler`, `will-navigate`, `will-attach-webview` and `web-contents-created` across `electron/` returned nothing. Preload scripts re-run on **every** navigation within a webContents, so a main window navigated cross-origin — or a `window.open()` — hands the destination page the whole `window.redstartAPI` surface. CSP does not stop this: `default-src` does not constrain top-level navigation and `navigate-to` was never shipped by anyone. `installNavigationContainment()` denies window-open and `<webview>` attachment flatly (nothing in the launcher uses either) and cancels any navigation away from the launcher's own location. Hung off `app.on('web-contents-created')` rather than off `mainWindow`, so it covers webContents that do not exist yet — which is the set a per-window handler misses.
  - **`ipc/guard.mjs` is now the only registrar.** All 55 `ipcMain.handle` sites across the ten `ipc/*.mjs` modules go through a `handle()` wrapper that validates in order: a trusted window is registered at all (unset → reject, so it fails closed), `event.sender` identity, a non-null `senderFrame`, `senderFrame === sender.mainFrame`, and the frame's URL. The wrapper owns `event`, so every handler body and its `(_, arg)` signature is unchanged — mechanically a rename.
  - **The URL check is not redundant with the identity check, and this is the detail this pattern usually gets wrong.** `webContents.mainFrame` still resolves to the current main frame *after* a cross-origin navigation, so identity alone still passes for a navigated window. Only the URL pins the origin. There is a test that fails if that step is removed.
  - **`file://` origins are all the string `"null"`.** Verified, not assumed: `new URL('file:///E:/…/dist/index.html').origin === "null"`, and so is every other `file://` URL's. An origin allowlist would therefore have accepted **any local HTML file** in a packaged build, including one an attacker dropped on disk. So the packaged branch compares the resolved *pathname* against the known `dist/index.html` and only the dev branch compares an origin. `WebFrameMain.origin` also postdates Electron 33, so `.url` is what gets read.
  - **The predicate lives in its own module (`renderer-location.mjs`) rather than inside the guard**, because navigation containment needs the same predicate and `createWindow()` needs the same *values*. `createWindow()` now loads from it too, so what is enforced and what is loaded cannot drift.
  - **Live SSRF fixed: `mcp:test-external` never called `validateExternalMcpUrl`** — while `mcp:add-external` three lines above it did. Main-process SSRF that bypassed the `external-mcp-url.mjs` control outright, reachable today with no renderer compromise at all. It also called `url.endsWith()` on an unchecked value, so a non-string argument threw a `TypeError` out through the channel. Both fixed; the probe now runs exactly the validation the registration path does.
  - **Argument shapes on the 11 mutating channels (`ipc/validate.mjs`), and nowhere else.** `settings:set-binary-path` requires an absolute, existing `.exe` (a falsy value still means "clear it" — that is the Reset button); `settings:set-models-dir` requires an absolute path and, on refusal, returns the folder actually in effect so the UI never shows a setting that did not take; the seven `capabilities:set-*` handlers reject a non-object instead of throwing a bare `TypeError` out of a destructure, and refuse a relative `rootDir`; `auth:set-required` demands a literal boolean, because a stray `''` must not read as "turn auth off"; `models:download` checks shape at the edge (the *values* were already checked deeper, in `assertValidRepoId`/`destinationFor`, and that stays authoritative). Read-only handlers like `models:publishers` are deliberately untouched — schema-ing those buys nothing and is where this kind of work stalls. **Hand-rolled, ~60 lines, no zod:** a schema library for eleven call sites does not earn its place in an installer, and this repo already hand-rolls its primitives (`path-scope.mjs`, `external-mcp-url.mjs`, the PNG encoder in `index.mjs`).
  - **A wrapper every handler *remembers* to use is a convention, not an invariant.** New suite `scripts/test-ipc-guard.mjs` (17 checks) fails the build on any raw `ipcMain.handle` outside `guard.mjs`, and on any bare `ipcMain.on` anywhere — there are currently zero, and since the guard only wraps `handle`, a future listener would be an unguarded channel with no way to reject. Comments are stripped before scanning, since `guard.mjs` legitimately names the raw call while explaining why not to use it. Deliberately **not** a global monkey-patch of `ipcMain` at startup: same guarantee, invisible, and it would fight the recording stub the IPC suites are built on.
  - **The adversarial half drives real handlers with forged events** — wrong webContents, a subframe, a navigated frame, a null `senderFrame`, a `senderFrame` that throws because the frame was destroyed, and the no-window-pinned case. Target is `settings:set-binary-path` because it is the head of the chain, and **every rejection also asserts `settings.json` on disk is byte-identical afterwards**: a guard that refuses the call but writes the value anyway would pass a return-value assertion and fail the actual security property.
  - **Verified non-vacuous by mutation.** Dropping the frame-URL check and reverting one module to `ipcMain.handle` turned exactly the two corresponding checks red (15/17); restoring both returned 17/17.
  - `scripts/test-ipc-contract.mjs` now stands up a trusted window before invoking handlers, since the guard correctly refuses a call with none. Both suites share `scripts/lib/fake-ipc-event.mjs`. Wired into `test:security` **and** `ci.yml` together — `test-ci-parity.mjs` hard-fails if only one is updated.
  - **The binary path is re-checked on the way OUT, not just on the way in.** Validating `settings:set-binary-path` protects new writes; it does nothing about the value already sitting in `settings.json` on every install shipped so far, which `resolveBinary()` reads and `ipc/server.mjs` spawns. Checking only at the write would leave stored values trusted forever, so `resolveBinary()` now runs the same predicate and falls through to the bundled binary on a refusal — the same thing it already did when the path did not exist.
  - **The packaged branch is tested even though it cannot be smoke-tested.** A dev run exercises only the `localhost:5173` path; the `file://` comparison is what ships, and it fails in the worst direction — get it wrong and every IPC call in the installed app is refused and the launcher is inert. The suite flips the stub's `isPackaged` and asserts the real `dist/index.html` is accepted, that no other local file is (all four candidates confirmed to have origin `"null"` first, so the test proves the footgun is actually being avoided), and that a query string, a fragment or a lowercase drive letter still match.
  - **Verified against a dev run:** the UI loads and a model launches with the guard and containment in place. Also confirmed the launcher has no `window.open`, no `target="_blank"`, and no hash routing, so the flat window-open denial breaks nothing and no fragment can reach the packaged URL comparison.
  - **The packaged build is now verified too, by driving the real binary — `npm run smoke:packaged`.** This was the last gap: every `scripts/test-*.mjs` runs against the Electron stub where `isPackaged` is false, so the whole suite *and* every dev run exercise the `localhost:5173` branch and neither touches the `file://` branch that ships. `scripts/smoke-packaged.mjs` launches the packaged exe with `--remote-debugging-port` and drives its renderer over CDP (Node 22+ has a global `WebSocket`, so no dependency): 11 checks covering the loaded URL, guarded IPC round-trips **from the real packaged frame**, the three navigation-containment events that have no unit coverage at all, and the log showing both denials with zero false refusals. - **Tool permissions and file-system powers — the whole six-phase plan, from `redstart-tools-permissions-discussion.md` (working tree, alongside branch `test/ipc-and-gateway-coverage`).** Two live security problems closed, four bugs fixed, and a delete tool shipped. Design record in `redstart-tools-permissions-plan.md`; decisions and their reasoning are there rather than repeated here. The recurring theme is worth stating once: **every problem below was silent.** Nothing errored, nothing failed a test, and in two cases the system confidently reported the opposite of the truth.
  - **The model was being offered two complete filesystem APIs on two different machines.** Inside Twig, `fs_*` tools act on the *user's PC* and Nest's File System capability acts on the *server* — and the model had all 22, with nothing in any description saying which machine it would touch. The protection had been accidental: Nest's file tools were once *also* named `fs_*`, and the chat-ui deduped by name with the local ones first. The FS MCP migration renamed Nest's side to the upstream names, the collision vanished, and the shadowing stopped happening — no error, no failing test, no log line. Precedence is now keyed on **capability identity** carried in `_meta` on `tools/list`, so a future rename breaks a lookup loudly instead of dissolving a safety property quietly. Descriptions now name the machine.
  - **Any signed-in user could read every other user's files.** `list_documents` enumerated the shared documents root to every caller and `/files/download` authenticated the caller and then resolved paths against the shared roots with **no account scoping at all** — and filenames are server-derived slugs, so they were guessable even without the listing. Documents, File System and Scholar are now per-account (`user_files/<slug>-<id>/`), keyed on the account **id** rather than the username, because `createAccount` validates uniqueness only — a username of `../../etc` or `CON` would otherwise have become a traversal or create-failure primitive. Fixed **structurally**: another account's path resolves inside *your* folder and 404s, so there is no ownership check to forget on one of the three code paths that reach the same bytes.
  - **Tool bans were never enforced at the MCP server.** `buildGatewayConfig` computed `disabledTools` and handed the same object to both consumers; only `tools-gateway.mjs` read it. So a banned tool was stripped from the completions payload and hidden in the UI while the built-in MCP server on `port + 2` still advertised it *and still executed it* on a direct `tools/call` — which is what every MCP client does, because that is the transport. The ban's own copy ("removed for every connected client") was false exactly where it mattered. Now enforced at both chokepoints, with a regression test that calls a banned tool directly.
  - **`delete_file` — the first destructive tool, and the gate that had been waiting for it.** `evaluateToolPolicy`, `allowDestructive`, the default-off config and the UI toggle all already existed and gated nothing, because the pinned upstream filesystem server ships no delete. Classifying one Redstart-owned tool as `destructive` armed all of it. Deletion goes to the OS recycle bin (falling back to `.trash/<timestamp>/` inside the caller's own storage) — **nothing in the codebase destroys data**; a delete that cannot be made recoverable fails and leaves the file where it was. Guards: never the storage root, never a non-empty directory (there is deliberately no `recursive` option), and a symlink is deleted as a *link*.
